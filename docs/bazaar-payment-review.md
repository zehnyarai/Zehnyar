## Implemented in source

- The Bazaar-specific `PaymentsScreen` obtains product prices from the Cafe Bazaar billing catalog and uses those values in the package list. The selected Bazaar purchase button now repeats the selected assessment count and the catalog price before the billing flow opens.
- The screen states that the first two assessments are free, one purchased credit unlocks one full assessment, and packages are one-time consumable products—not subscriptions or auto-renewals. Persian and English copy are both maintained.
- Bazaar SKU mapping is `assessment_1`, `assessment_3`, `assessment_6`, and `assessment_12`. The app calls Bazaar purchase APIs and does not render the manual card-transfer or receipt-upload cards in the Bazaar-specific UI branch. This is a source-level observation; the actual Bazaar APK must still be checked to ensure the build flag is set.
- Backend purchase registration verifies Bazaar's signed purchase data, the expected package ID, known SKU, purchased state and installation payload; it grants credits idempotently by order ID. The app consumes the Bazaar purchase only after the backend accepts/registers it. A failed registration leaves it available for retry/recovery.
- The application leaves two full assessments available without payment, satisfying the source-level free-use path. No subscription product or auto-renewing billing path is implemented.

Relevant implementation: `mobile/src/screens/PaymentsScreen.js`, `mobile/src/i18n/dictionary.js`, `mobile/src/core/bazaarBilling.js`, and `backend/app/payments.py`. Operational product setup notes are in `docs/payments-operations.md`.

## Open release checks and risks

1. **Catalog prices and RSA key are matched at the dashboard/source level.** The supplied screenshots show all four expected SKUs, active status, one-time-purchase type, and the intended prices: 6,000,000 / 12,000,000 / 25,000,000 / 45,000,000 rial. The RSA public key shown in Bazaar settings matches the app and backend constants. Product descriptions and the actual buyer checkout price have not been checked. The separate dynamic-discount JWT key was visible in a screenshot; the project contains no use of that key, so reset it in the Bazaar panel and do not share the replacement. No secret value is stored in this repository.
2. **Cross-device / reinstall portability is not solved.** The balance is stored on the backend against a random installation ID, not an authenticated Bazaar account or transferable user account. Consumed purchases are not a durable restore mechanism. Reinstalling or moving to another device creates a new installation ID, so previously purchased remaining credits may not follow the purchaser. The supplied policy says paid products must work across devices on which the app is installable. Resolve this entitlement/restore design before public release, or obtain explicit written guidance from Cafe Bazaar; do not claim cross-device access today.
3. **Network availability is part of redemption.** After purchase, the client requires the HTTPS backend to verify the receipt and grant credits, and assessment credits are consumed through the backend when online. The code leaves a purchase unconsumed when registration fails so it can be retried, but an already-granted balance is not a robust offline, cross-device entitlement. Define and test behavior for server outage, reinstall, app update and device change.
4. **Price parity outside the Bazaar build needs confirmation.** The direct/manual-transfer build has the same four nominal package amounts in source. The Bazaar panel's actual amounts are unknown. Compare the identical digital products and ensure any product purchasable outside the Bazaar app is not cheaper there than inside Cafe Bazaar. No out-of-app purchase link is shown in the Bazaar payment screen source.
5. **Refund and support handling need an owner.** The supplied policy describes refund requests through Bazaar/developer support. No public support contact or operational refund procedure was verified in the submitted build. Confirm the publisher's support address and operational responsibility, without putting credentials or purchase secrets in the app.
6. **APK verification remains required.** Build the Bazaar variant and inspect the installed artifact and runtime: app/package ID, actual purchase screen, absence of card-transfer/receipt/manual checkout and external purchase links, all four catalog prices, test purchase, signature verification, idempotent credit grant, purchase consumption/recovery, two free assessments, and current/update behavior. No real purchase or refund has been performed here.

The two-free-assessment path is source-level only and has not been exercised on a Cafe Bazaar-installed device. Product-panel setup and the cross-device entitlement issue are release blockers. Do not describe the Bazaar variant as payment-policy compliant or release-ready until those checks are closed.
