# امضای ثابت اندروید و حفظ کلیدهای ثبت‌شده

## وضعیت واقعی ــ ۱۹ اکتبر ۲۰۲۶

- هویت امضای ثابت **هنوز فعال نشده است**: `android/signing-identity.json` عمداً `not_configured` است؛ اثرانگشت ساختگی در آن نیست.
- اتصال فعلی عامل به GitHub، برای فهرست Secrets مخزن پاسخ `403 Resource not accessible by integration` داده است. داشتن امکان push، مجوز مدیریت Secrets نیست.
- در این تغییر، کلید خصوصی انتشار ساخته/بارگذاری نشده و APK جدیدی منتشر نشده است. آزمون‌های محلی صرفاً هویت‌های موقت آزمایشی، در پوشهٔ موقت مستقل می‌سازند؛ این‌ها هویت انتشار نیستند.
- APK تاریخی ۰.۸.۱ و فایل‌های مشخصات آن بدون تغییر حفظ شده‌اند. لینک نصب قبلی از صفحهٔ نصب برداشته شده تا به‌عنوان «به‌روزرسانی سازگار» پیشنهاد نشود.

**برنامهٔ موجود را حذف نکنید و داده‌های آن را پاک نکنید. کلیدهای سرویس تحلیل را هم در چت ارسال نکنید.** کلیدهای ثبت‌شده به‌خاطر این تغییر از نصب فعلی حذف نمی‌شوند.

## چه مشکلی اصلاح شده و چه چیزی هنوز حل نشده است؟

کلیدهای دو سرویس، جداگانه در خزانهٔ رمزگذاری‌شدهٔ دستگاه ذخیره می‌شوند. باز و بسته کردن برنامه، تغییر سرویس یا خطای اتصال نباید آن‌ها را حذف کند. اما نگهداری داده هنگام به‌روزرسانی اندروید علاوه بر ذخیره‌سازی درست، به همان شناسهٔ بسته و امضای سازگار نیاز دارد.

روش قبلی در هر ساخت کلید امضای تازه تولید می‌کرد. این مسیر حذف شده است. از این پس، هر دو workflow نصب‌کننده تنها با یک گواهی ثابت و اثرانگشت ثبت‌شده اجازهٔ انتشار دارند. نبودن کلید، رمز، اثرانگشت، تطابق گواهی یا نسخهٔ جدیدتر باعث توقف انتشار می‌شود؛ هیچ fallback تصادفی یا debug برای نصب‌کنندهٔ قابل توزیع وجود ندارد. ساخت unsigned و fixtureهای debug صرفاً برای آزمون CI ادامه دارد، نه برای نصب روی گوشی مالک.

**یک امضای ثابت تازه، امضای تصادفی APKهای قدیمی را بازسازی نمی‌کند.** کلید خصوصی تاریخی در اختیار این محیط نیست و از خود APK یا گواهی عمومی قابل استخراج نیست. بنابراین سازگاری با برنامه‌ای که اکنون روی گوشی مالک نصب است تضمین/تأیید نشده؛ نباید فایل جدیدی را به‌عنوان راه‌حل آن معرفی کرد. تا داشتن مسیر انتقال امن و واقعاً آزموده، همان نصب باید حفظ شود.

پشتیبان دفتر باغ جایگزین خزانهٔ کلیدهای API نیست؛ نباید فرض کرد فایل پشتیبان عمومی، کلیدهای رمزگذاری‌شدهٔ AndroidKeyStore را بعد از حذف/نصب مجدد برمی‌گرداند.

## فعال‌سازی امن توسط مالک مخزن

این کار فقط یک بار برای هویت انتشار انجام می‌شود؛ با کلیدهای Gemini/Grok ارتباطی ندارد و نیازی به ثبت دوبارهٔ آن‌ها ندارد.

1. اتصال GitHub در Arena باید مجوز **Actions Secrets: read/write** برای `zehnyarai/Zehnyar` داشته باشد. در صورت محدودیت اتصال، مالک مخزن می‌تواند دستور زیر را در یک checkout امن روی دستگاه خودش، با GitHub CLI احراز هویت‌شده و OpenSSL اجرا کند. هیچ توکن/رمزی نباید در چت وارد شود.
2. روی همین شاخه، از ریشهٔ مخزن اجرا شود:

   ```bash
   python3 tools/configure-android-signing.py
   ```

3. ابزار ابتدا دسترسی Secrets را بررسی می‌کند. اگر پیکربندی قبلی وجود داشته باشد یا Secrets ناشناخته‌ای با نام‌های امضا پیدا کند، آن‌ها را بازنویسی نمی‌کند. سپس یک PKCS12 رمزگذاری‌شده با RSA-3072 می‌سازد؛ گواهی SHA-256 با اعتبار تقریباً ۳۰ سال است. رمز تصادفی در آرگومان خط فرمان یا خروجی چاپ نمی‌شود.
4. نسخهٔ خصوصی در `.private/android-signing/` می‌ماند؛ این مسیر از Git و context ساخت Docker کنار گذاشته شده است. **فایل PKCS12 و رمز آن باید در محل امن خارج از فضای موقت عامل، با دسترسی محدود و نسخهٔ پشتیبان قابل بازیابی نگهداری شوند.** از دست دادن آن‌ها می‌تواند ادامهٔ انتشار به‌روزرسانی را غیرممکن کند. هیچ‌کدام را commit، پیوست چت یا منتشر نکنید.
5. ابزار فقط این دو Secret را از stdin به GitHub می‌فرستد:
   - `PESTINO_ANDROID_KEYSTORE_B64`
   - `PESTINO_ANDROID_STORE_PASSWORD`

   کلید و مخزن، در این پیکربندی یک رمز دارند. برای مخزن واردشده با رمز متفاوت، signer امکان `PESTINO_ANDROID_KEY_PASSWORD` را دارد؛ ابزار فعلی مسیر واردکردن هویت تاریخی نیست.
6. فقط پس از موفقیت هر دو بارگذاری، اثرانگشت **عمومی** در `android/signing-identity.json` ثبت می‌شود. فقط همین JSON عمومی را بازبینی و commit کنید. اجرای مجدد بعد از پیکربندی مجاز نیست؛ بعد از بارگذاری ناقص، اجرای مجدد از همان پشتیبان خصوصی استفاده می‌کند، نه کلید تازه.
7. پیش از اولین انتشار ثابت، نسخه در package/lock و `versionName` و `versionCode` اندروید را هماهنگ افزایش دهید؛ فعلاً نسخهٔ آرشیوی ۰.۸.۱/۲۱ است. ابزار عمداً بازنویسی APK آرشیوی یا استفادهٔ مجدد از versionCode را رد می‌کند. اولین APK ثابت همچنان به‌عنوان به‌روزرسانی نصب‌های تصادفی قدیمی عرضه نمی‌شود.

تغییر امضای ثابت پس از انتشار ممنوع است. ابزار `SIGNING.json` تحویل قبلی را هم کنترل می‌کند. بازیابی فقط باید با همان کلید خصوصی/رمز و اثرانگشت ثبت‌شده انجام شود؛ حذف اثرانگشت یا Secrets برای «رفع خطا» راه‌حل نیست.

## کنترل‌های انتشار

- `tools/sign-compat-apk.sh` هیچ کلیدی تولید نمی‌کند. ابتدا تنظیمات عمومی و Secrets لازم را بررسی می‌کند، سپس کلید را در پوشهٔ موقت خصوصی باز می‌کند و گواهی واقعی را با اثرانگشت پین‌شده تطبیق می‌دهد.
- پس از امضای v1/v2/v3، `apksigner` امضای واقعی APK را بررسی می‌کند. فقط یک امضاکننده با همان SHA-256 پذیرفته می‌شود. فایل‌های خصوصی موقت در خروج پاک می‌شوند.
- `SIGNING.json` شامل اثرانگشت عمومی، SHA-256 فایل، نام/نسخه، versionCode و commit منبع است؛ هیچ کلید خصوصی یا API در آن قرار نمی‌گیرد. این سابقه به‌خودی‌خود سازگاری با نصب تاریخی را اثبات نمی‌کند.
- اگر هویت آماده نباشد، CI گزارش صریح «Android update not published» می‌دهد؛ job تحویل و artifact نصب‌کننده اجرا نمی‌شوند. سبز بودن آزمون‌ها به معنی انتشار یا حل ناسازگاری نصب قدیمی نیست.
- هر دو حالت مستقل و آنلاین از یک signer استفاده می‌کنند. جابه‌جایی بین حالت آنلاین و مستقل، مهاجرت دادهٔ آزموده‌شده محسوب نمی‌شود.

## حدود آزمون نگهداری داده

`tools/check-key-storage.sh` فقط برای شبیه‌ساز تازه و یک‌بارمصرف CI است؛ در پایان fixtureها را uninstall می‌کند و **نباید روی گوشی مالک اجرا شود**.

آزمون جدید هر دو کلید **ساختگی** را ذخیره می‌کند، پردازش را می‌بندد، **همان APK آزمایشی** را با `adb install -r` و بدون uninstall یا پاک‌کردن داده بین دو مرحله نصب می‌کند؛ سپس ثابت بودن UID و خوانده‌شدن هر دو مقدار رمزگذاری‌شده را بررسی می‌کند. این آزمون حفظ داده در package replacement هم‌امضا را می‌سنجد؛ نه ارتقای بین دو نسخهٔ تولید، نه امضای متفاوت، نه اتصال حساب واقعی مالک. نتیجهٔ واقعی اجرای API 24 و API 35 باید در اجرای CI همین commit بررسی شود.
